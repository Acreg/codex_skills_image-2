# 并发调度与逐图验收

只在用户请求多张独立图片时读取。并发复用已有原生工具或已授权 API 入口，不创建子代理、后台监控或新调度服务。它减少独立请求排队时间，不保证上游推理变快。

## 调度

1. 按用户要求给每张图分配任务 ID（如 poster-a、poster-b）、提示词及互不相同的输出路径。只生成用户要求的数量，不为了挑选额外扩图。修改依赖前图、连续编辑或以首图为参考的后续图必须串行。
2. 技能不人为设置并发数量上限。按用户请求的数量，使用宿主允许的实际并行能力提交独立任务；只有用户指定、宿主执行能力或服务商实际限流才约束同时运行数量，不擅自把它改成固定分批。依赖关系仍须遵守，不能承诺无限资源或绕过服务商限制。
3. 原生优先：用宿主明确提供且允许包装该图片工具的并行调用能力，一张图对应一次调用；不能把不支持的系统工具塞进仅接受开发者工具的包装器。无并行能力就串行，并如实说明，不能靠文字伪装并发。
4. API 仅在用户已同意接口来源、数量和可能计费后使用。通过宿主现有并行执行能力同时运行已有 `generate_image.py`，每条命令都指定独立 `--out`，工作目录始终是项目；不另写批量脚本、不将密钥放进任务表或命令行。不要并行调用会修改共享配置的命令。
5. 每次完成先记录实际任务 ID、调用/进程 ID、输出和状态，再决定是否补充下一个。记录保存在当前项目的本次产物目录，纯文本即可，不记录密钥、认证内容或图片 Base64。遇到失败/限流/结果未知时停止补发尚未提交的任务，继续收集已发出请求的结果；不杀掉可能已计费的请求、不自动重试。告诉用户哪些已完成、哪些未发出。

## API 并行命令示例

从项目目录通过宿主的并行执行工具分别执行以下两条命令。`<python>`、`<skill-root>` 必须现场解析；需要时明确选定同一种 `--config-source`，不在并发中混用不同提供商。

```text
<python> -B <skill-root>/scripts/generate_image.py generate --prompt "第一张图的要求" --out output/imagegen/poster-a.png
<python> -B <skill-root>/scripts/generate_image.py generate --prompt "第二张图的要求" --out output/imagegen/poster-b.png
```

示例文件已存在时换用唯一新名称，不能默认加 --force。

## 防止串图

有原生附件就按各自工具调用关联交付，不做日志恢复。确需恢复时，每张图用独立 prepare 状态和独立输出；可在并发发送之前逐一准备，但恢复每张图时必须给出该任务已确认的 `--call-id`，不能按返回顺序、完成时间或“最新图片”猜。

```text
<python> -B <skill-root>/scripts/native_delivery.py deliver --state output/imagegen/poster-a.delivery.json --call-id <A实际调用ID>
<python> -B <skill-root>/scripts/native_delivery.py deliver --state output/imagegen/poster-b.delivery.json --call-id <B实际调用ID>
```

多个候选无法准确绑定时停止该图恢复并说明，不重复生图。

## 逐图验收

每张完成后按其自身提示词验图，不把 A 的要求套到 B。基本符合的先交付并简评，不必等最慢的一张；明显不符的指出“哪一张、哪项要求、实际偏差”，询问是否只重做该图。用户确认前不重做，也不把已通过的图全批重新生成。重做是新的可能计费请求，保留旧产物且使用新文件名。
